# Step 023 — 容差怎么定：把它放宽会掩盖什么

**你会做出**：一个明确的容差策略，写进代码注释，而不是拍脑袋的 `1e-5`。

**为什么是现在**：Phase 05 要和 onnxruntime 逐层对拍，Phase 07 要 GPU 和 CPU
对拍。这两处的容差如果拍脑袋定，你会陷入最糟的状态：**分不清"数值噪声"
和"真 bug"**。

## 需要知道的（8 分钟）

绝对误差 `|a-b|` 在数值本身很大时会误报；相对误差 `|a-b|/|b|` 在数值接近 0 时
会误报。实际都用混合判据：`|a-b| <= atol + rtol * |b|`（numpy 的 `allclose` 就是）。

## 动手

1. `bool allclose(const Tensor& a, const Tensor& b, float rtol, float atol)`，
   返回是否全部通过，并**输出最大偏差出现在哪个索引**。
2. 报告要包含：max abs diff、max rel diff、以及它们各自的位置。
   只说"不通过"的对拍工具没用。
3. 为 matmul 定一个有依据的容差：K 次累加，每次相对误差上界 eps/2
   （float32 eps ≈ 1.19e-7），最坏情况约 `K * eps`。把这个推导写进注释。

## 跑起来

```bash
cmake --build build-cpu --parallel && ./build-cpu/tt tol-demo
```

## 你应该看到

```
matmul K=3    max_abs=0.000000e+00  max_rel=0.000000e+00  -> pass (rtol=1e-5)
matmul K=1024 max_abs=1.220703e-04  max_rel=3.2e-07 at (17,43) -> pass (rtol=1e-5)
```

K 大时绝对误差明显变大，但相对误差还在界内——这正是为什么不能只用 atol。

## 卡住了

- K=1024 时相对误差超过 1e-5 → 检查累加变量是不是 float。
  如果确实是，把 rtol 放宽到 `K * eps` 的量级并**在注释里写明依据**。

### 🎯 Additional goal — 放宽容差会掩盖什么（可选）

**假设**：把 rtol 从 1e-5 放宽到 1e-2，一个"只算了一半 K"的 matmul bug
仍然会被抓到；但一个"漏掉最后一行"的 bug 在某些输入下会被放过。

**做什么**：故意引入三个 bug，在 rtol = 1e-5 / 1e-3 / 1e-2 / 1e-1 下各跑一遍
对拍，记录哪些组合能抓到：

1. K 循环写成 `k < K-1`（漏最后一项）
2. 输出最后一行不写（保留 `empty()` 的未初始化内容）
3. `A[i][k] * B[k][j]` 写成 `A[i][k] * B[j][k]`（B 转置了）

**测什么**：3×4 的表格，每格填"抓到 / 放过"，以及抓到时的 max_rel。

**你可能会发现**：bug 3 在任何容差下都会被抓到（结果完全不同）；
bug 1 在大 K 时反而**更难**抓到（漏 1/1024 的贡献只改变 0.1%）；
bug 2 取决于未初始化内存里恰好是什么——**这正是 Step 004 不清零的理由**，
如果你清了零，bug 2 会变成"结果偏小"，看起来很像数值误差。

**为什么会这样**：容差是一个**关于误差来源的假设**。它假设唯一的误差来源是
浮点舍入。任何不是舍入的错误（逻辑错、漏写、索引错）只要幅度小于容差就会溜过去。
容差越宽，能溜过去的 bug 类别越多。

**这个结论什么时候不成立**：FP16 和 INT8 的固有误差本来就大，
那时必须放宽容差——但同时必须换用**任务级指标**（比如 top-1 是否一致）
而不是只看逐元素误差。这是 Phase 09 的事。

**写下来**：3×4 表格 → 哪个 bug 最难抓 → 为什么 → 你最终选的容差和依据。
