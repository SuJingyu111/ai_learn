# Step 018 — 广播的两种实现：展开 vs 索引映射

**你会做出**：一个显式物化广播结果的版本，与 Step 017 的 stride-0 版本并存。

**为什么是现在**：这是引擎里第一个"同一语义，两种实现"的地方。
后面每一次优化决策都是这个形状。现在用最简单的例子把对比方法练熟。

## 动手

1. `add_materialized(a, b)`：先把两个输入各自 `expand_to(shape).contiguous()`
   物化成完整大小，再走最简单的线性相加。
2. 保留 Step 017 的 `add`（stride-0，不物化）。
3. 两者必须对同样输入给出**完全相同**的结果——加一条测试断言这件事。

## 跑起来

```bash
cmake --build build-cpu --parallel && ./build-cpu/tt op-demo broadcast-compare
```

## 你应该看到

```
add             (1000,1) + (1,1000) -> (1000,1000)  checksum=... 
add_materialized(1000,1) + (1,1000) -> (1000,1000)  checksum=...
checksums match: yes
```

两个 checksum 必须一致。

## 卡住了

- checksum 不一致 → 物化版本的 `expand_to` 大概率写错了；
  用小 shape（3×4）dump 两边的完整结果逐个对。

### 🎯 Additional goal — 物化广播的代价（可选）

**假设**：`(1000,1) + (1,1000)` 这种"小输入、大输出"的情况下，
物化版本要多分配和写入 2×10⁶ 个 float（8 MB），会明显更慢；
但如果输入本来就接近输出大小，两者差别很小。

**做什么**：用 `engine/bench` 的 harness 测两个版本，各跑至少 30 次。
测两组形状：
- `(1000,1) + (1,1000)` → `(1000,1000)`（极端广播）
- `(1000,1000) + (1000,1000)` → `(1000,1000)`（完全不广播）

**测什么**：median / p95 / min，以及每个版本的峰值内存
（`/usr/bin/time -l` 在 macOS，`-v` 在 Linux）。

**你可能会发现**：极端广播下物化版慢 2–5×；不广播时两者几乎相同
（因为 `expand_to` 什么都不用做）。如果极端广播下两者一样快，
先确认你的物化版本真的分配了 8 MB——打印一下 `nbytes`。

**为什么会这样**：物化多了一次 8 MB 的写入和一次读取，
而这些字节放不进 L2，每一个都要走内存。stride-0 版本读的是同样的
1000 个元素上千次——它们一直待在 L1 里。

**这个结论什么时候不成立**：如果广播后的张量要被**反复使用**多次，
物化一次可能比每次都做 stride-0 间接寻址更划算。
真实 runtime（包括 ORT）确实两种都有，按上下文选。

**写下来**：假设 → 两组形状的实测数据 → 结论 → 边界条件。
