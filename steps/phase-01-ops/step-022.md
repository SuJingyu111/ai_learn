# Step 022 — 浮点不结合：为什么 sum 顺序会改变结果

**你会做出**：一个能亲眼看到 `(a+b)+c != a+(b+c)` 的 demo。

**为什么是现在**：下一步要定容差，而定容差之前必须先搞清楚**误差从哪来**。
更重要的是：Phase 07 上 GPU 后，reduction 的求和顺序必然和 CPU 不同，
到那时你的对拍会开始出现"结果不完全一样但好像也没错"的情况。
现在理解它，那时才不会误判成 bug。

## 先手算

float32 只有 24 位尾数，能精确表示的最大连续整数是 2²⁴ = 16777216。
那么 `16777216.0f + 1.0f` 等于多少？

据此推断：`(16777216 + 1) + 1` 和 `16777216 + (1 + 1)` 分别是多少？

## 动手

1. `tt fp-demo` 打印上面两个表达式的结果。
2. 再做一个规模化的版本：把 1/1、1/2、… 1/1000000 用 float32 累加，
   分别按**正序**、**逆序**、**两两配对（树形）**三种顺序求和。
3. 用 float64 算一个参考值。

## 跑起来

```bash
cmake --build build-cpu --parallel && ./build-cpu/tt fp-demo
```

## 你应该看到

最小例子：

```
(2^24 + 1) + 1 = 16777216
2^24 + (1 + 1) = 16777218      <-- 不同
```

调和级数 float32 累加（前 100 万项）：

```
forward   = 14.3573580
reverse   = 14.3926516
pairwise  = 14.3927307
float64   = 14.3927268    <-- 参考
```

**正序的误差最大**，差了 0.035——相对误差约 0.24%。

## 卡住了

- 三种顺序结果一样 → 你在某处用了 `double` 做累加。
  累加变量必须是 `float`，中间结果也要 `static_cast<float>` 回去。
- 最小例子两个都是 16777216 → 检查是不是编译器把常量折叠成了 double 计算。
  把值放进 `volatile float` 或从命令行读入。

## 记住这三件事

1. **正序累加长序列会持续损失精度**，因为累加和越来越大，后面的小项被吃掉。
2. **树形求和精度更好**，而且它正好是 GPU reduction 的天然形状。
   numpy 的 `sum` 内部就是 pairwise，所以你和 numpy 对拍时，
   如果你用正序，差异会比想象的大。
3. 误差**不是 bug**，但它有上界。下一步就是把那个上界写下来。
